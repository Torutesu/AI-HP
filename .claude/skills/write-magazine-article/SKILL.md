# マガジン記事の執筆

このスキルは、共有のSEO/LLMOパイプライン（7ステップ）に沿って、有益・オリジナル・
人間のための記事を1本書き、`lib/magazine.ts` に追加する。Googleと生成AI検索の
双方から評価される（インデックス・ランキング・引用される）ことをゴールにする。

## 最初に読むファイル（毎回）

記事の品質は、思いつきで書かず、リポジトリの一次資料に紐づけることで担保する。
着手前に必ず読む:

- `content/keyword-backlog.md` — 着手できるキーワードと検索意図。**ここに無い
  トピックは書かない**（勝手にトピックを広げない）。
- `content/product-definition.md` — 自社サービスの「できること／できないこと」。
  サービスへの言及は必ずここと照合する。
- `content/quality-checklist.md` — 自己採点の基準（合格85点）。
- `content/review-checklist.md` — 公開前に人間レビュアーが使う最終チェック。
  記事は必ずこのレビューを経てから公開する（自動公開しない）。
- `lib/magazine.ts` — 記事データと `Article` 型。既存記事と重複しないか、
  カテゴリ、関連記事候補、書式を確認する。
- 編集方針（`app/editorial-policy/page.tsx` の内容）— 一次情報主義・出典明示・
  時点明記・非保証注記。

## このスキルの鉄則

- **自動公開しない。** 記事は必ず `status: "draft"` で作り、人間のレビューを
  経てから公開する。書き終えたら「レビューパケット」を提示して止まる（手順7）。
- **浅く書かない。** 一般論の羅列で終わらせない。具体例・手順・トレードオフ・
  数字（出典付き）まで踏み込む。分量の下限は手順4に従う。
- **ファクトチェックできない主張を本文に残さない。** 事実は出典を付けるか、
  自社の枠組み／意見として明示する。確認できない点は本文から外し、レビュー
  パケットに「要確認」として列挙する（手順3）。

## 手順

### 1. キーワード選定（勝手に選ばない）
引数でキーワード／slugが指定されていればそれを使う。無ければ
`keyword-backlog.md` の「バックログ」から優先度順に1件提案し、ユーザーに確認する。
バックログにも無いトピックを頼まれたら、書く前に「バックログに無い」ことを伝え、
追加するか確認する。バックログが残り3本を切っていたら知らせる。

### 2. 検索意図の確定
書き始める前に、意図を1つ確定する（比較／ハウツー／定義／購入ガイド／
トラブル対応／リスト）。以降の構成はこの意図に正面から答える形にする。

### 3. 商品検証＋ファクトチェック
自社サービスに触れる箇所は、`product-definition.md` の「提供していること」だけを
根拠にする。「提供していない／主張しないこと」は書かない。数値は `/cases/` の
シミュレーション値と整合させ、必ず非保証の注記を付ける。

事実に関わる主張（統計・制度・法令・相場・他社事例・固有名詞つきの数字）は、
次のいずれかにする。曖昧にぼかして逃げない。
- **出典を付ける**：制度・統計・公的情報は Web検索で一次情報（公式サイト・
  官公庁・原典）を確認し、本文に出典を `[名称（発行元）](URL)` で示す。時点
  依存なら「◯年◯月時点」を添え、詳細は公式で確認するよう促す。
- **自社の枠組み／意見として書く**：一次情報が無い経験則は「私たちの支援の
  現場では」等と主体を明示し、事実の断定と区別する。
- **確認できないものは本文に出さない**：代わりにレビューパケットへ「要確認」
  として列挙し、人間の確認に委ねる。

補助金・制度・最新モデルなど鮮度が命のトピックは、**必ずWeb検索で最新の
一次情報にあたる**。知識だけで金額・要件・締切を書かない。

### 4. 固定構造で執筆（浅くしない）
`Article` オブジェクトを1つ作る。フィールドと本文ブロックの規約は「記事データ
の書式」を厳守する。要素は必ず揃える:
- キーワードを含む **title**
- 冒頭 **summary**（結論先出し2〜4文。読者と生成AIが結論を先に得る）
- **body**：`## 見出し` / `- 箇条書き` / `※注記` / 段落 / インラインリンク
- **faq**：3問前後（記事末＋FAQPage構造化データになる）
- **related**：関連記事slug 3件（トピッククラスター。カテゴリ横断可）
- 本文の結びは無料相談（`/contact`）へ自然につなぐ

**深さ・分量の下限**（一般論で薄く埋めない）:
- 柱記事（ハウツー／定義／比較）：本文おおむね **2,500〜4,000字**、`##`
  セクション **5〜7本**。各セクションに、抽象論だけでなく具体例・手順・
  判断基準・トレードオフのいずれかを必ず入れる。
- 「なぜそうなるか」「どう見分けるか」「何に注意するか」まで踏み込む。
  読者が次の行動を取れる粒度にする。
- 数字を出すなら出典か非保証注記を必ず添える（手順3）。

### 5. アンチスロップ推敲（2パス）
1st: 誇張語（劇的・圧倒的・革命的 等）／空虚なマーケ文句／薄いフック質問
（「〜ではないでしょうか」）／根拠なき主張を削る。
2nd: 文頭の反復、弱い接続（そして・また）の多用、長すぎる段落、そして
**ダッシュ「——」の多用**を直す。「——」は原則使わず、句読点・括弧（　）・
接続で表現する（AIの典型的な癖のため）。

### 6. 自己採点＋差し戻し
`quality-checklist.md` で自己採点する。特に **A 人間らしさ**、**B 事実性**
（product-definition・出典との一致）、そして**深さ・分量**（手順4の下限）を
重視。85点未満、または A/B が配点の6割未満、または分量が下限に満たない場合は
ステップ4へ戻して改稿してから進む。自己採点はレビューの代わりにはならない。

### 7. 下書きで止める（自動公開しない）
記事は人間のレビューを経てから公開する。ここでは**下書きとして反映し、止まる**。
- 完成した `Article` を `lib/magazine.ts` の `rawArticles` に追加する。**必ず
  `status: "draft"` を付ける**（一覧・サイトマップ・RSS・検索に出ず、URLで
  プレビューだけできる。記事上部にレビュー中バナーが出る）。
- `date` は当日（`YYYY.MM.DD`）。不明なら確認する。
- `npm run build` でビルドが通ることを確認する（`/magazine/<slug>` が生成され
  型エラーが無いこと）。失敗したら直す。
- **レビューパケットを提示して止まる**（下記）。ここでコミット・公開はしない。
- `keyword-backlog.md` の該当行は、まだ published にしない（レビュー通過後）。

#### レビューパケット（人間レビュアーへ渡す）
記事本体に加えて、次を簡潔に提示する:
- プレビューURL（`/magazine/<slug>/`。ローカルなら `npm run dev`）
- **主張と出典の一覧**：事実に関わる記述と、その裏付け（出典URL／自社の枠組み
  である旨）の対応表
- **要確認リスト**：自分では確証を取れなかった点（数字・制度・締切など）
- 自己採点の結果（合計点と、A/B/深さの評価）
- 想定キーワードと検索意図

### 8. 公開（人間の承認後のみ）
ユーザー（レビュアー）が承認したら:
- 対象記事の `status` を `"published"` にする（または `status` 行を削除）。
- `content/keyword-backlog.md` の該当行を `published` にし、slug を記す。
- ビルドを通し、ユーザーが求めればコミット／プッシュする。
- レビューで直しが入った場合は反映し、必要なら `updatedAt` を当日にする。

## 記事データの書式（`lib/magazine.ts` の `Article`）

`rawArticles` 配列に、この形のオブジェクトを追加する。TypeScript として妥当で
あること（文字列内にそのままの `"` を入れない。改行は箇条書きで `\n` を使う）。

```ts
{
  slug: "kebab-case-en",              // 英小文字・ハイフン。URLになる
  category: "コスト削減",              // CATEGORIES のいずれか（下記）
  title: "キーワードを含む日本語タイトル",
  date: "2026.07.18",                 // 当日
  status: "draft",                    // 新規は必ず draft（承認後に published へ）
  // updatedAt: "2026.07.18",         // 改稿時のみ
  excerpt:
    "一覧カード・meta・OG用の要約1〜2文（結論の予告。summaryとは別）",
  summary:
    "冒頭の要点。結論先出しで2〜4文。記事の核心の問いに直接答える。",
  body: [
    "導入の段落。",
    "## セクション見出し",
    "段落。関連記事へは [ラベル](/magazine/other-slug) でインラインリンクできる。",
    "- 箇条書き1\n- 箇条書き2\n- 箇条書き3",   // 1文字列・改行区切り
    "## まとめ",
    "結びの段落。無料相談（/contact）へ自然につなぐ。",
    "※時点依存や数値には注記（例：効果を保証するものではありません）。",
  ],
  faq: [
    { q: "想定質問1？", a: "自己完結した1段落の回答（単独で引用されても読める）。" },
    { q: "想定質問2？", a: "回答。" },
  ],
  related: ["slug-a", "slug-b", "slug-c"],  // 実在するslug。トピッククラスター
}
```

カテゴリは `CATEGORIES` の5つから選ぶ:
`コスト削減` / `売上向上` / `事例・シナリオ` / `経営・組織` / `技術トレンド`

本文ブロックの描画ルール（`app/magazine/[slug]/page.tsx`）:
- `"## テキスト"` → セクション見出し（h2）
- `"- a\n- b"` → 箇条書き（1文字列に改行区切りで複数項目）
- `"※テキスト"` → 小さめの注記（免責・時点）
- `"[ラベル](/magazine/slug)"` → 本文中インラインリンク（内部リンク）
- それ以外 → 段落

## トーンの指針
既存記事に合わせる。実務者が書いたように、経営の数字（コスト・売上・利益率）に
引きつけて具体的に。断定より根拠。過度な期待も過小評価もしない。日本語として
自然な改行・句読点。1段落=1論点。

## 既存記事の推敲に使う場合
新規執筆と同じ基準（ステップ5・6）で、対象記事の `body`/`summary`/`faq` を
改稿する。事実（数値・出典・サービス記述）は変えず、AIっぽさの除去と構造の
充足を優先する。`updatedAt` を当日に更新する。
