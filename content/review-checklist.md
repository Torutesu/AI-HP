# 公開前レビュー チェックリスト（人間レビュアー用）

> 記事は自動公開しない。`status: "draft"` の記事を、公開（`published`）に
> 変える前に、人間がこのチェックを通す。AIの自己採点（`quality-checklist.md`）は
> 通過の前提だが、それだけでは公開しない。最終判断は人間が行う。

## 使い方

1. 下書きのプレビューを開く（`/magazine/<slug>/`。ローカルは `npm run dev`）。
   上部に「レビュー中の下書き」バナーが出ていることを確認する。
2. スキルが出した**レビューパケット**（主張と出典の一覧／要確認リスト／自己採点）
   を手元に置く。
3. 下記を確認する。1つでも「いいえ」があれば、直すまで公開しない。

## 事実性（最優先）

- [ ] 事実に関わる数字・制度・法令・相場・他社事例に、**確認できる出典**がある
      （公式サイト・官公庁・原典）。または「自社の枠組み／経験則」と明示している。
- [ ] レビューパケットの**「要確認」項目を実際に確認**し、裏が取れないものは
      本文から落とした。
- [ ] 時点依存の記述に「◯年◯月時点」があり、詳細は公式で確認するよう促している。
- [ ] 自社サービスの記述が `product-definition.md` の範囲内（できないことを
      書いていない）。効果を断定せず、シミュレーション値には非保証注記がある。
- [ ] 実在しない機能・受賞・取引先・顧客名を書いていない。

## 深さ・有用性

- [ ] 一般論の羅列で終わっていない。具体例・手順・判断基準・トレードオフがある。
- [ ] 検索意図（比較／ハウツー等）に正面から答え、読者が次の行動を取れる。
- [ ] 分量が薄すぎない（柱記事で本文2,500字以上・セクション5本以上が目安）。

## 品質・体裁

- [ ] 人間が書いたように読める（機械的な反復・空虚な言い回しがない）。
- [ ] ダッシュ「——」の多用・誇張語・薄いフック質問がない。
- [ ] 構造が揃っている（要点／キーワードを含むタイトル／見出し／FAQ／内部リンク／
      CTA）。内部リンクのリンク先が実在し、リンク切れがない。
- [ ] タイトル・要点・本文の主張が一致している（タイトル倒れでない）。

## 承認

- [ ] 上記すべてOK。→ `status` を `"published"` にし、`keyword-backlog.md` の
      該当行を `published` にする。ビルドを通して公開する。

差し戻す場合は、どのチェックで落ちたかを具体的に伝えて改稿を依頼する。
